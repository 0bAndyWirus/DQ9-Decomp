# Internal GPU3D raster interface contract

This is a project-compatibility contract, not a claim of hardware accuracy. The blind implementer must observe `GPU3D_RASTER_HANDOFF.md` and the behavioral specification and fixtures. All inputs and sinks are synchronous and borrowed only for the duration of a call. Results on invalid or non-finite inputs outside the stated domain are not specified.

## Coordinates and values

`RasterInputVertex` contains homogeneous `(x,y,z,w)`, unprojected U/V in texture-coordinate units, and RGB in the caller's color units. `RasterScreenVertex` has floating-point scaled-target pixel coordinates, NDC `z = clip.z / w`, reciprocal W, U/W, V/W and RGB/W. A `RasterVertex` has signed 28.4 scaled-target pixel X/Y and seven floats in order: 1/W, **normalized** Z `(clip.z/w + 1)/2`, U/W, V/W, R/W, G/W, B/W. Normalized Z is not NDC Z. `RasterBoundary` X and Y are integer scaled-target pixels and its seven values use that same order. `RasterSpan` X and width are integer scaled-target pixels; its seven values and deltas refer respectively to the first pixel and successive pixels. `RasterFragment` coordinates are integer scaled-target pixels, RGB and UV are unweighted, and depth is a 24-bit integer. `front` denotes front-facing.

The packed viewport bytes from least to most significant are X1, Y1, X2, Y2. Width and height are `((end - start) mod 256) + 1`, even when endpoints wrap. Let `yb = Y1` for Y1 ≤ 191, otherwise `Y1 - 255`. For nonzero effective W, screen X is `scale * (X1 + (x/W + 1)*width/2)` and screen Y is `scale * (192 - (yb + (y/W + 1)*height/2))`; Y grows downward. These equations specify coordinate meaning, not permission to reassociate floating-point calculations where that changes fixture outputs.

## Operations

* `raster_plane_distance(vertex, plane)` returns signed distance, with nonnegative inside: plane 0 `x+w`, 1 `w-x`, 2 `y+w`, 3 `w-y`, 4 `z+w`, 5 `w-z`. Only indices 0–5 are part of the contract. These operations also serve BOX_TEST, whose visibility behavior must remain unchanged.
* `interpolate_raster_clip(a,b,t)` returns the componentwise linear interpolation of all four clip coordinates, UV and RGB, from `a` toward `b`; neither input is mutated. BOX_TEST uses these two operations directly and requires their exact output, independently of polygon clipping.
* `clip_raster_polygon(input,count,attributes,output)` accepts up to 16 ordered vertices and returns the retained count, at most 16. The first returned-count entries of both mutable `input` and `output` contain the same ordered clipped polygon on normal completion. Count zero at entry or a fully rejected intermediate polygon returns zero; the output is not guaranteed to be written on an early return. With attribute bit 12 clear, any input vertex beyond the far plane rejects the entire polygon immediately, leaving both arrays unchanged; otherwise all six planes are clipped. On a zero-count return, do not assume `input` is unchanged except for that immediate far rejection. Intersections and retained attributes obey the specification. The return count, not the original count, governs every consumer; BOX_TEST has its own face clipping and uses the two preceding helpers rather than this function.
* `project_raster_screen(clip,u,v,color,viewport,scale)` returns a screen vertex. If `abs(w) < 1e-20`, every returned field is zero; otherwise it uses the original W, including negative W, for projection and perspective weights. Its Z is NDC, not normalized.
* `raster_ceil_fixed(value)` converts signed 28.4 to integer pixels by mathematical ceiling, including negative values; inputs must fit the result type.
* `prepare_raster_polygon(vertices,count,viewport,attributes,scale,result,front_facing)` accepts 3–10 already-clipped vertices, projects them and returns acceptance after face selection (attribute bit 6 enables back, bit 7 front). On success it writes `count` projected vertices and facing. The returned order is suitable for traversal and need not preserve the submitted starting vertex or winding. On failure callers must not rely on output fields. Unlike screen projection, this path substitutes positive `1e-8` for exactly zero W; nonzero W is retained. Scaled screen X/Y multiplied by 16 are clamped to ±1,000,000 then converted to signed integers by truncation toward zero. Its Z is normalized, as above.
* `traverse_raster_polygon(vertices,count,y_begin,y_end,sink)` consumes the successful prepared polygon and synchronously emits boundary pairs in increasing row order for covered rows in `[y_begin,y_end)`. Boundaries describe left and right integer X and associated seven values. A row's output must be identical regardless of its band, including rounding accumulated before the band. The caller owns and processes the resulting spans.
* `prepare_raster_span(left,right,target_width,span)` returns false for no positive-width span after horizontal clipping; output is unspecified on false. On success X and width describe the intersection with `[0,target_width)`. Values and per-pixel deltas represent interpolation across the original, unclipped span. For each component the first surviving value is the original left value plus its per-pixel delta multiplied by the number of pixels removed on the left: compute this prestep as one multiply-add, not as repeated additions. Its rounded result is independently observable and may differ from sequential stepping. `advance_raster_values` adds each delta once to its corresponding value; successive samples use successive additions.
* `raster_four_samples(current,step,more,a,b,c,d)` is available on x86-64. In each lane, `a` is the original `current`, and `b`, `c` and `d` are respectively the values after one, two and three successive scalar float additions of that lane's `step`. These results must match sequential scalar rounding exactly, not multiplication by a lane index. If `more` is true, `current` becomes the result of the fourth successive addition; otherwise it remains unchanged.

* `traverse_wire_triangle(a,b,c,attributes,w_depth,width,y_begin,y_end,sink)` consumes three screen vertices. It emits fragments within the width and half-open row interval in row-major order, after face selection by bits 6/7. Samples are at pixel centers. A triangle with absolute signed screen area below `1e-12` emits nothing. A sample with any barycentric weight below `-1e-6` is excluded. When polygon alpha bits 16–20 are zero, only samples whose minimum weight is at most `0.02` are emitted; otherwise all accepted interior samples are emitted. Interpolate reciprocal W and weighted UV/RGB and divide to recover UV/RGB; skip a sample when the absolute interpolated reciprocal W is below `1e-20`. Z-depth is `floor(clamp((NDC_Z+1)/2,0,1)*4194303) << 2`; W-depth is `clamp(floor((1/interpolated_inv_w)*4096),0,0xffffff)`. The caller performs all subsequent fragment tests and shading.
* `prepare_raster_dot(screen,vertex,w_depth,width,height,y_begin,y_end,fragment)` floors screen X/Y to select one pixel; returns false outside the target or row interval. On success it writes X/Y, the unweighted original vertex UV/RGB, and depth. Z-depth uses the wire formula on screen NDC Z; W-depth is `clamp(floor(vertex.clip.w*4096),0,0xffffff)`. It does not set `front`; the caller owns facing and dot enablement, including the one-dot W cutoff. Output is unspecified on failure.

## Ownership and scheduling

The caller owns destination buffers, shading, texture sampling, depth and stencil tests, blending, fog, edge processing and packing. Polygon submission and per-pixel fragment order remain compatible. Inline rendering may request the full target interval; disjoint band intervals may run concurrently with immutable inputs, writing only their owned rows. The caller synchronizes before neighbor-row operations or publication. No shared mutable raster scratch may introduce cross-band dependence.

Godot's `DsRasterMesh` also uses polygon preparation and row traversal; it converts the resulting boundaries and attributes into mesh geometry rather than duplicating the raster edge walker.

At scale `s` (1–4), target width is `256*s`, height is `192*s`; row bounds and all screen coordinates use scaled pixels. Native and scaled outputs are separate targets. Inline and banded outputs must match exactly, including auxiliary fields.

Full enhanced geometry changes the caller's storage and polygon selection, not
this raster interface: the caller retains hardware-limited Classic output and
manages the separate enhanced output and its fallback. Both paths pass the
same clipped-vertex, viewport, scale and attribute contract to the raster
operations. The expanded polygon list does not change guest-visible hardware
counts or permit changing the pinned Classic fixture outputs.

## Validation and limits

The golden fixture test captures 131 pre-refactor scenes in 2,096 full-output snapshots across two scheduling modes, four scales and two capture modes, plus 12 ordered clip-output goldens. `dsr_raster_boundary_tests` separately checks direct interface behavior, including BOX_TEST helpers, clipping mutation/count, projection thresholds, viewport quantization and wire/dot depth and coverage. These are project outputs, not hardware truth; preserve them without regeneration. They constrain sampled behavior only. The integration owner separately runs existing GPU3D tests and the pinned ladder; passing these does not resolve provenance or prove general hardware accuracy. Further independent fixtures are needed for unobserved ties, numerical thresholds and degenerate cases.
